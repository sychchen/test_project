# 基于 akshare 源码的行情面板 + 选股策略方案建议

> 调研对象：`D:\kiro-worspace\test_project\akshare`（akshare 源码仓库，版本 1.18.95）
> 调研日期：2026-09-16
> 结论先行：**akshare 数据覆盖足够全，可直接 import 使用；但它只是"抓取层"——无缓存、无落库、无策略引擎。建议复用现有 stock-system 的 MySQL + FastAPI + 前端体系，把 akshare 作为补充数据源接入，而不是另起炉灶。**

## 一、akshare 目录里有什么（实测盘点）

### 1.1 仓库结构

| 目录 | 内容 |
|---|---|
| `akshare/akshare/` | 源码本体，按资产类别分包：`stock/`、`stock_feature/`、`stock_fundamental/`、`index/`、`fund/`、`futures/`、`bond/`、`option/`、`forex/`、`economic/` 等 |
| `akshare/docs/` | Sphinx 文档，`docs/data/stock/` 有各接口示例 |
| `akshare/tests/` | 只有注册表/发布检查，**无接口级测试** |
| `akshare/scripts/` | 构建脚本（build_registry.py） |
| `pyproject.toml` | Python ≥3.11；核心依赖 pandas≥2.0、requests、curl_cffi、beautifulsoup4、lxml、mini-racer（同花顺 JS 签名） |

### 1.2 A 股数据能力（函数均在 `akshare/akshare/` 下，统一返回 `pd.DataFrame`）

| 能力 | 关键接口 | 数据源 | 对应现有 stock-system |
|---|---|---|---|
| 实时快照 | `stock_zh_a_spot_em` / `stock_zh_a_spot` | 东财 / 新浪 | ✅ 已有（腾讯/新浪快照） |
| 日线历史 | `stock_zh_a_hist` / `stock_zh_a_daily` | 东财 / 新浪 | ✅ 已有（新浪 K 线） |
| 分钟线 | `stock_zh_a_hist_min_em` / `stock_zh_a_minute` | 东财 / 新浪 | ✅ 已有（新浪分钟） |
| 指数 | `stock_zh_index_daily` / `_tx` / `_em` | 新浪/腾讯/东财三源 | ✅ 已有（双源） |
| 板块（行业/概念） | `stock_board_concept_*` / `stock_board_industry_*`（含成分股、历史、分钟） | 东财 | ⚠️ 已有表但成分股仅 2,563 只，**东财源可扩容** |
| 资金流 | `stock_fund_flow_individual/concept/industry/big_deal` | 同花顺 | ⚠️ 现有仅新浪历史资金流，**可补个股/板块当日流** |
| 龙虎榜 | `stock_lhb_detail_em` 等 | 东财 | ✅ 已有 `stock_billboard` |
| 大宗交易 | `stock_dzjy_mrmx/mrtj` | 东财 | ✅ 已有 `stock_block_trade` |
| 涨跌停池/强势股 | `stock_zt_pool_em`、`stock_zt_pool_strong_em`、`stock_zdhtmx_em` | 东财 | ❌ **缺失，选股高价值因子** |
| 估值 | `stock_value_em`、`stock_a_all_pb`、`stock_market_pe_lg` | 东财/乐咕 | ❌ 缺失（baostock 估值已废） |
| 两融/港资/人气 | `stock_margin_em`、`stock_hsgt_em`、`stock_hot_rank_em` | 东财 | ❌ 缺失 |

### 1.3 关键限制（必须正视）

1. **无持久化**：全库 grep 无 sqlite/sqlalchemy/parquet 落库代码，仅个别 `lru_cache`。每次调用都是实时 HTTP 抓取。
2. **直连第三方**：requests + curl_cffi 硬刚东财/新浪/同花顺接口，存在频控/封禁风险（我们在新浪双域名上踩过 456 挑战页的坑，东财 push2his 也封过）。
3. **无策略层**：只有选股向数据接口（`stock_institute_recommend` 机构评级、涨停池等），没有回测/信号引擎，策略逻辑必须自研。
4. **接口变动风险**：akshare 本质是爬虫集合，目标站改版即失效——用源码版（而非 pip 包）的好处是可以自己修。

## 二、总体建议：不重建，做"数据源增强"

现有 stock-system 已经有完整的 **采集 → MySQL → FastAPI(:8600) → ECharts 前端 → 选股策略（run_pick.py）** 闭环。akshare 的定位应该是：

```
akshare 源码（import 调用）
   │  新增采集器（复用现有去重/UPSERT/双校验套路）
   ▼
MySQL 5.5（新增表，沿用 stock_* 命名）
   │
   ▼
FastAPI :8600 新增 /api/* 端点
   │
   ▼
app/web/index.html 新增面板（沿用 .panel-body/scroll-tbl 既有布局坑位经验）
   │
   ▼
run_pick.py 新策略（新因子入库后直接参与选股）
```

**不建议**单独用 akshare 搭一套独立面板——那会丢掉已有的 513 万行日线历史、滚动窗口预热、批次去重等积累，且 akshare 无落库，面板每次实时抓取会被频控打死。

## 三、分期实施建议

### 第一期：补齐高价值缺失因子（数据采集层）

优先级按"选股价值 × 现有缺口"排序：

| 优先级 | 接入接口 | 新建表 | 价值 |
|---|---|---|---|
| P0 | `stock_zt_pool_em` / `stock_zt_pool_strong_em`（涨停池/强势股） | `stock_zt_pool` | 短线选股核心因子，现有体系完全没有 |
| P0 | `stock_value_em` / `stock_a_all_pb`（估值） | `stock_valuation` | 补上 baostock 估值废弃后的空洞 |
| P1 | `stock_fund_flow_individual`（同花顺个股资金流） | 并入/对照现有资金流表 | 与新浪资金流交叉验证 |
| P1 | `stock_board_industry_cons_em` 等（东财板块成分） | 扩充 `stock_board_member` | 解决成分股仅 2,563 只的源侧限制 |
| P2 | `stock_hot_rank_em`（人气榜）、`stock_margin_em`（两融） | `stock_hot_rank` / `stock_margin` | 情绪面因子 |

工程要点（沿用已有教训）：
- 采集器照抄现有 `collect_*` 模式：限速（新浪经验 ~0.83 req/s/域）、失败重试、断点续传。
- **滚动窗口指标必须先预热再写库**（多抓 25 根 → 丢 NaN → tail），这是 09-16 刚修过的坑。
- MySQL 5.5 无 hash join：大表统计一律单表 GROUP BY + Python 合并。
- 长耗时回填走后台任务。

### 第二期：行情面板增强（展示层）

- 复用 `app/web/index.html`，新增面板而非重写：
  - **涨停池面板**：今日涨停/炸板/连板梯队表格（`scroll-tbl` 容器，避开 sticky th 压行坑）。
  - **估值面板**：个股市盈率/市净率历史分位曲线。
  - **资金流对比面板**：新浪 vs 同花顺双源资金流对照。
- 前端坑位提醒（已有记忆）：
  - `.panel-body` 是 flex 列，新块需加白名单 `flex:0 0 auto`；
  - 图表实例统一 `getChart(dom)`，面板 innerHTML 重建后要防画到废节点；
  - 改后端必须重启 uvicorn（无 --reload）。

### 第三期：选股策略（策略层）

## 四、风险与对策

| 风险 | 对策 |
|---|---|
| akshare 接口因目标站改版失效 | 用的是源码不是 pip 包，可直接改 `akshare/akshare/` 下对应文件修复；采集器加响应结构校验，失败落日志 |
| 东财/同花顺频控封禁 | 沿用新浪经验：限速 + 失败退避；关键数据双源互备（东财挂了切新浪） |
| 实时接口拖慢面板 | 面板一律读 MySQL，不允许前端触发实时抓取；实时数据由后台定时采集 |
| MySQL 5.5 性能 | 新表加 (ts_code, trade_date) 联合索引；统计查询单表 GROUP BY |

## 五、一句话结论

**akshare 值得接入，但定位是"数据采集增强包"：第一期先把涨停池、估值、同花顺资金流、东财板块成分四类缺口数据采进 MySQL，面板和策略在现有 stock-system 骨架上长出来，不另起炉灶。**

## 六、方案 B：全新独立项目（不复用 stock-system）

> 2026-09-17 补充：如果把 akshare 当成全新项目的唯一数据底座，不从现有 stock-system 继承任何东西，方案如下。

### 6.1 与方案 A 的本质差异

| 维度 | 方案 A（接入现有） | 方案 B（全新项目） |
|---|---|---|
| 历史数据 | 直接拥有 513 万行日线/4.2 年 K 线 | 需重新回填（新浪 datalen 无上限，约 1-2 天可补完日线） |
| 数据库 | 受 MySQL 5.5 限制（无窗口函数/hash join/CTE） | **可自由选型，甩掉历史包袱** |
| 策略体系 | 在 run_pick.py 上加策略 | 可设计声明式策略框架 |
| 前端 | 受现有单 HTML 布局坑位约束 | 可上真正的前端工程 |
| 上线速度 | 快（P0 两周内） | 慢（框架搭好再谈业务，约 4-6 周到同等功能） |
| 适用场景 | 快速验证想法、个人使用 | 长期演进、多人协作、正式产品化 |

### 6.2 全新项目分层架构

```
┌─────────────────────────────────────────────────┐
│ 展示层   Vue3/React SPA 或 Streamlit + ECharts    │
├─────────────────────────────────────────────────┤
│ API 层   FastAPI（REST + WebSocket 推送实时行情） │
├─────────────────────────────────────────────────┤
│ 策略层   策略框架（声明式配置）+ 回测引擎          │
├─────────────────────────────────────────────────┤
│ 指标层   因子计算管道（pandas/polars，预热滚动窗） │
├─────────────────────────────────────────────────┤
│ 存储层   PostgreSQL+TimescaleDB / DuckDB+Parquet │
│          + Redis（实时快照缓存）                  │
├─────────────────────────────────────────────────┤
│ 采集层   akshare 源码 import + 调度器（限速/重试/ │
│          断点续传/双源互备/响应校验）             │
└─────────────────────────────────────────────────┘
```

**全新项目必须自建、akshare 不提供的能力**（这是方案 B 的真正工作量）：

1. **采集调度器**：APScheduler/Celery 定时任务 + 每源限速器（token bucket）+ 失败退避重试 + 断点续传水位表。akshare 一个都不给。
2. **数据模型**：维度表（`dim_stock` 股票主数据）+ 事实表（`fact_daily_quote` / `fact_minute_quote` / `fact_snapshot` / `fact_fund_flow` / `fact_zt_pool`）+ 因子表（`fact_factor_daily`）+ 信号/选股表（`fact_signal` / `fact_pick_batch`）。
3. **因子管道**：滚动窗口指标（MA/MACD/量比）统一在管道里算好落库，**预热逻辑内置**（多取 w-1 根再截断），不允许查询时现算。
4. **策略框架**：策略 = 声明式配置（因子条件 + 权重 + 闸门）而非硬编码脚本；配统一回测引擎验证后再进实盘选股。
5. **实时链路**：盘中快照走"定时采集 → Redis → WebSocket 推送"，前端永不直连第三方。

### 6.3 全新项目的避坑清单（从 stock-system 实战提炼）

- 采集与展示必须分离：面板只读库/缓存，实时抓取是后台任务的事——否则东财/新浪频控直接打死面板。
- 滚动窗口指标写库前必须预热，受限窗口直接 `rolling(20)` 会把前 19 行 NaN 用 NULL 覆盖正确值，形成永久空洞。
- 新浪单域稳态限速 ~0.83 req/s（突发 150-200 次即 456 挑战页），东财 push2his 有封禁史——限速器和双源互备是必需品不是奢侈品。
- 数据源返回结构要做校验（如新浪 dict → 定长数组归一化），目标站改版时第一时间报警而不是静默写脏数据。

## 七、技术栈选型（方案 B 选定后）

### 7.1 推荐技术栈（按档位）

| 层 | 轻量档（个人/快速验证） | 标准档（推荐，长期演进） | 重量档（多人/产品化） |
|---|---|---|---|
| 语言/运行时 | Python 3.11+（akshare 硬性要求 ≥3.11） | 同左 | 同左 |
| 依赖管理 | **uv**（akshare 仓库自带 uv.lock，直接对齐） | uv + venv | uv + Docker |
| 数据库 | **DuckDB + Parquet**（零运维，分析快） | **PostgreSQL 16 + TimescaleDB**（分区/窗口函数/CTE，治 MySQL 5.5 所有痛点） | PostgreSQL 集群 + Citus |
| 缓存 | 不需要 | **Redis**（盘中快照 + 限流计数） | Redis 哨兵 |
| 采集调度 | APScheduler（进程内） | APScheduler + 后台常驻 | Celery + Redis Broker |
| API | FastAPI + uvicorn | FastAPI + uvicorn（+ WebSocket） | FastAPI + Nginx 反代 |
| 数据处理 | pandas | **polars**（大数据量快 10 倍+）或 pandas | polars + DuckDB 混合 |
| 回测 | 自研事件循环（100 行内） | **vectorbt**（向量化，快） | vectorbt pro / qlib |
| 前端 | **Streamlit**（纯 Python，1 天出面板） | **Vue3 + Element Plus + ECharts**（工程化，长期维护） | React + AntD + ECharts |
| 部署 | Windows 本地 + 后台任务 | Windows 本地 / Linux + systemd | Docker Compose |

### 7.2 关键选型决策逻辑

**数据库——全新项目最重要的一个决定**：
- 选 **PostgreSQL 16 + TimescaleDB** 的理由：hypertable 自动按时间分区（513 万行日线查询不再靠索引硬扛）、窗口函数/CTE/hash join 全有（现有系统多少 SQL 是被 MySQL 5.5 逼成"单表 GROUP BY + Python 合并"的）、`ON CONFLICT` UPSERT 成熟。
- 选 **DuckDB + Parquet** 的理由：单人本地项目零运维，列存天然适合 K 线分析，pandas/polars 直读。代价：并发写入弱、没有现成 UPSERT，不适合多人或多进程同时写。
- **不建议再用 MySQL 5.5 起步**——除非要复用现有库，否则没有任何理由。

**前端——按"谁来用"选**：
- 自己看 → Streamlit，开发效率碾压一切，且 Python 全栈不用写 JS。
- 要长期演进成正式产品 → Vue3 + Element Plus + ECharts（中文社区熟，组件全）；现有系统的单 HTML 模式到 3-5 个面板后维护成本会失控，全新项目不要再走这条路。

**回测——先自研后引入**：策略不超过 5 个时，自研向量化回测（pandas 几十行）比引入框架更可控；策略复杂化后再上 vectorbt。qlib 太重，个人项目不建议。

**akshare 的接入姿势**：源码目录直接加入项目（git submodule 或 vendored copy），不装 pip 包——目标站改版时能自己改 `akshare/akshare/` 下的文件立即修复，这是用源码版的核心理由。

### 7.3 最终建议

| 你的情况 | 建议 |
|---|---|
| 想快速验证选股想法 | **方案 A**（接入现有 stock-system），技术栈不用选，两周内 P0 落地 |
| 想做长期演进的新平台 | **方案 B 标准档**：uv + FastAPI + PostgreSQL/TimescaleDB + Redis + APScheduler + vectorbt + Vue3/ECharts |
| 只有一个人、怕运维 | **方案 B 轻量档**：uv + FastAPI + DuckDB/Parquet + Streamlit，一周内能跑出第一版 |

### 7.4 路线决策（2026-09-17 已确认）

**已定：先方案 A 验证，后方案 B 重建。**

1. **当前执行**：方案 A 一期 P0 —— 涨停池/强势股（`stock_zt_pool_em`）+ 估值（`stock_value_em`）采集进现有 stock-system（MySQL + run_collect.py 体系），akshare 以 vendored 源码方式接入。
2. **触发重建的条件**：P0/P1 因子入库后，用 2-4 周实盘选股验证策略有效性；若策略成立且现有骨架（MySQL 5.5 / 单 HTML 前端）成为演进瓶颈，则按方案 B 标准档（uv + FastAPI + PostgreSQL/TimescaleDB + Redis + Vue3）重建，历史数据从 MySQL 迁移。
